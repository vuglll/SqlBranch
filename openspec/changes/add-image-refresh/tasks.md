# Tasks

Start only after `add-pool-format-upgrade` is archived. Every Docker test in every group is an integration test tagged so it runs only when `SQLBRANCH_IT=1`. Format-2 pools in tests come from `pool upgrade --yes` (integration) or the format-2 test helper of `add-pool-format-upgrade` (unit). "Regenerate the agent skill" means `dotnet run --project src/SqlBranch.Cli -- skill export --dir skills/sqlbranch --force` and committing `skills/sqlbranch/`; the unit suite's comparison must pass. Each task that adds a format-2-only option also gates it: on a format-1 pool it exits 3 `pool_upgrade_required` after exit-2 checks, `docker_unavailable`, `not_initialized` and `engine_stopped`, with zero pool changes; during an unfinished upgrade the write options exit the same way and `image list --versions` keeps working.

## 1. Verify platform assumptions

This group runs first after approval, on the maintainer's Linux machine, where Docker is available. Record environment, date, observed results and source links in `docs/research/2026-11-19-image-refresh-facts.md`. A failed spike means revising design.md before relying on the fact.

- [ ] 1.1 Measure free bytes before and after staging, restore, masking, sealing, publish and prune on a thin and a copy pool with one retained version, for a local backup, a URL backup and a script that grows the database. Inject exhaustion before staging, before restore and during growth. Verify: old version checksums unchanged, branch reads succeed, exit 1 with `pool_full` naming measured free and known required bytes, and the phase table is in the research note.
- [ ] 1.2 Time a fixed read/write workload alone and while a restore and masking script run, with a barrier inside masking to test reads, commits and an independent create before publication. Then hold a shared `sqlbranch:catalog:shop` lock in one session and, in turn, (a) issue a waiting exclusive `sp_getapplock` from a second session and (b) poll it with `@LockTimeout = 0` every 250 ms; in each case request a new shared lock from a third session. Verify: zero lost writes and zero dropped sessions; throughput and p50/p95 latency for both workload runs; whether the new shared request in (a) waits behind the queued exclusive one, and that in (b) it is granted at once. All results are in the research note; if (b) ever delays the shared request, revise D3.
- [ ] 1.3 On directory and loop-xfs pools, one of them in copy mode, kill the writer and restart the engine on both sides of the catalog rename, each flush of a publication, and a prune unlink. Verify: exactly one complete current version, session locks of dead clients released, leftovers visible to a status probe, a retry succeeds, and surviving branches keep their rows. The crash matrix is in the research note.
- [ ] 1.4 Run a stub job (success, then a masking failure) under cron and a scheduled CI job on Linux, and under launchd and Windows Task Scheduler where a machine is available. Verify for each: working directory, tool discovery, secret injection, exit propagation, and that argv and logs hold no sentinel secret. Record each verified invocation. Record launchd and Task Scheduler as "not verified" when no machine was available; their examples then ship with that mark (task 7.1).

## 2. Catalog lock

- [ ] 2.1 Move create and reset from the shared image lock to a shared `sqlbranch:catalog:<name>` lock held from version selection through the branch record write (format 2 only; format 1 keeps the 0.2.2 locks). When the shared request meets an exclusive hold, retry with timeout 0 every 250 ms for a fixed 30 seconds, then exit 1 `catalog_busy` naming the image. Add the polling exclusive acquisition of D3 (timeout 0, retry until `publishWait`, stderr progress, `catalog_busy`) as a helper that holds the exclusive lock only around the catalog rename it is given and releases it before returning, so publication, `image rm` and prune can never hold it during file deletion (D3). Verify: fake-runtime tests that neither path ever issues a waiting request, that the exclusive helper honours `publishWait` with a fake clock and has released the lock when the rename callback returns, and that a create arriving during polling proceeds; fake-clock tests "Hold ends within the retry" and "Hold outlasts the retry"; integration test that a create completes while a poller holds no lock. Document the lock order and the 30-second retry in `docs/engine.md`.
